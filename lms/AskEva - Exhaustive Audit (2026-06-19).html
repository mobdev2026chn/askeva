AskEva CRM — Exhaustive Audit

A deep, code-level review of AskEva App - Merged.html and its ~45 linked JavaScript modules and ~30 stylesheets. Findings are grouped by the ten requested categories, each with severity, location, impact, root cause, a concrete fix, and a confidence rating.

Read this first — scope & method (honesty note)

This report is a deep, targeted audit, not a literal line-by-line transcription of all ~28k lines. Coverage was: full read of the integration shell (app-shell.merged.js) and the sync/real-time core (sync-layer.js); the persistence layer of leads-module.js; the merged HTML shell + inline scripts; plus high-signal pattern scans (innerHTML, JSON.parse, setInterval, document/window listeners, duplicate IDs, missing alt, filename collisions) across every root module.

Two framing facts that change how several requested checks apply:

  • This is a fixed-size phone mockup (.device = 412×892) centered in #stage and scaled to fit by fitStage() in profile.js. It does not reflow into a desktop layout, so the requested 768–1920px "layout break" checks mostly reduce to "does the scale-to-fit behave" — covered in §3.
  • This is a prototype with no backend. Auth, OTP, 2FA and sync are partly simulated. The §6 auth findings are real per your security brief, but several are by-design for a demo — flagged as such.

Confidence is marked per finding. High = directly verified in source. Medium = behavior reasoned from verified code. Low = needs runtime confirmation.

01

Functional Bugs

HighF-01 app-shell.merged.js · otpForm submit

OTP code is never verified — any 6 digits sign you in

Issue
The OTP form's submit handler only checks code.length < 6, then calls maybe2FA(). The actual digits entered are never compared to a sent code.
Impact
Login-with-OTP is bypassable with 000000 or any six digits. The "Verify it's you" step gives a false sense of security.
Root cause
No code is generated/stored when "Send OTP" fires (proceedToOtpCode just toasts), so there is nothing to validate against.
Fix
Generate and store a one-time code in sendOtp(), then in the submit handler compare code to it (and expire it). For a demo, hardcode an expected value and reject mismatches so the flow reads as real.
Confidence
High — handler reads if (code.length < 6) {…} hideErr(err); maybe2FA();
MediumF-02 app-shell.merged.js · maybe2FA / twofaForm

2FA gate silently bypasses when the security module is absent

Issue
maybe2FA() calls doLogin() directly unless window.__security.enabled() is truthy; the 2FA submit also does if (!window.__security || !window.__security.verifyCode) { doLogin(); }.
Impact
If settings-security.js fails to load (CDN/cache/script error) the entire 2FA requirement vanishes and any credential-format passes.
Root cause
Fail-open default. Missing dependency is treated as "no 2FA required" instead of "cannot verify → block".
Fix
Fail closed: if a user has 2FA enrolled but the verifier is unavailable, show an error and refuse login rather than waving them through.
Confidence
High
MediumF-03 app-shell.merged.js · registeredPhone()

Only one email can ever log in via OTP / reset password

Issue
registeredPhone() hardcodes a single map: { "eshan@tunepath.com": "9876544322" }. Every other address is rejected with "No account is registered with this email" in both Login-with-OTP and Forgot-password.
Impact
If a demo viewer signs up (the sign-up flow accepts any email) and then tries OTP login or password reset, they are permanently locked out — the sign-up never adds them to this map.
Root cause
Sign-up, OTP and reset are three disconnected flows; the "registered" check ignores accounts created in-session.
Fix
Have sign-up persist the new email→phone pair (e.g. localStorage) and have registeredPhone() consult it, or relax the gate for the prototype.
Confidence
High
MediumF-04 profile.js · fitStage() (line ~42)

Device rescales mid-typing when the mobile keyboard opens

Issue
fitStage() is bound to window resize and computes scale from window.innerHeight. On a real phone, focusing an input opens the soft keyboard, which shrinks innerHeight and fires resize → the whole phone visibly shrinks while the user types.
Impact
Jarring shrink/zoom on every text-field focus on touch devices; can also scroll the focused field out of view.
Root cause
No distinction between a true viewport resize and a keyboard-driven innerHeight change; no use of visualViewport.
Fix
Debounce, and ignore height-only shrinks while an input/textarea is focused; or base the fit on visualViewport and skip re-fit when document.activeElement is an editable field.
Confidence
Medium — logic verified; behavior is device-dependent.
LowF-05 app-shell.merged.js · setTitle()

signinTitle.firstChild.textContent assumes a text node

Issue
setTitle(t) writes to signinTitle.firstChild.textContent. If the title's first child is ever an element (icon/span) rather than a leading text node, this writes into the wrong node or throws.
Impact
Brittle to markup edits; a future title tweak could blank the heading or error silently.
Root cause
Relies on undocumented DOM ordering instead of a dedicated text target.
Fix
Wrap the title text in its own <span> and set that span's textContent.
Confidence
Medium
LowF-06 app-shell.merged.js · filterTickets()

Ticket priority filter is coupled to CSS class probing

Issue
Priority is derived by reading the badge's classes (prioEl.classList.contains("high")…) rather than a data- attribute. Status uses data-status, priority does not.
Impact
A purely visual class rename on .tk-prio silently breaks filtering with no error.
Root cause
Logic reads from presentation. Inconsistent with the status path right next to it.
Fix
Stamp data-priority on each .tk-card and filter on that.
Confidence
High

Responsiveness

fixed device · scale-to-fit
LowR-01 profile.js · fitStage()

Scale only shrinks, never enlarges — tiny phone on large monitors

Issue
scale = Math.min(sx, sy, 1) caps at 1, so at 1440px/1920px the 412×892 device sits at native size in a large empty field. Intended, but the surrounding canvas is unused space.
Impact
On desktop the app looks like a small phone floating in a void; reviewers may expect it to fill more of the screen.
Root cause
Deliberate "phone mock" framing; acceptable, noted for completeness against the 1280–1920 checks.
Fix
If a larger preview is wanted, allow scaling above 1 up to a sensible cap, or add a subtle device shadow/background to fill the stage.
Confidence
High
MediumR-02 profile.css · .device (412×892 fixed)

Short viewports (≈≤520px tall) scale text below comfortable size

Issue
Because the entire 892px-tall device is scaled uniformly to fit height, a short window (laptop with browser chrome, or landscape phone ~375px tall) drives scale well below 0.5, shrinking 24px body text to ~11px effective.
Impact
At 320–414px-tall / landscape orientations, content becomes hard to read and 44px touch targets shrink below the tap-friendly threshold.
Root cause
Whole-frame uniform scale rather than internal responsive reflow (expected for a device mock, but worth a minimum-scale guard).
Fix
Clamp a minimum scale and allow the device to scroll within the stage below it, so text never drops under a legible floor.
Confidence
Medium
LowR-03 .leads-secondary / #pfTabs (overflow-x:auto)

Horizontally-scrollable tab rows have no scroll affordance

Issue
Secondary tab rows and the profile tab strip use overflow-x:auto; scrollbar-width:none. With 6 profile tabs at 412px width, later tabs (Subscription, Transactions) are off-screen with no visible cue that more exist.
Impact
Discoverability: users may not realize tabs scroll; hidden tabs feel missing.
Root cause
Scrollbar hidden for aesthetics, no fade/chevron edge hint.
Fix
Add a right-edge gradient fade or a peeking partial tab so the overflow is visible.
Confidence
Medium
04

Accessibility

HighA-01 CSS: .lp-secrow span, .cp-row .v.link, et al.

Interactive <span>s are not keyboard- or screen-reader-operable

Issue
Several click targets are bare <span>/<div> with cursor:pointer and a JS click handler but no role, tabindex, or key handler — e.g. the "See all" link (.lp-secrow span) and linkified field values.
Impact
Keyboard and screen-reader users cannot reach or activate these actions; they're invisible to assistive tech.
Root cause
Styled-as-link spans instead of real <button>/<a>.
Fix
Use <button type="button"> (or <a>) for these actions; if markup must stay, add role="button" tabindex="0" and an Enter/Space handler.
Confidence
High
MediumA-02 sync-layer.js · sync chip

Sync state changes are not announced (no aria-live)

Issue
The status chip toggles between Synced / Syncing / Pending / Failed / Offline visually, but its only a11y hook is a static aria-label="Sync status". The offline banner and toasts likewise aren't live regions.
Impact
Screen-reader users get no notification when they go offline, a sync fails, or changes are queued — exactly the states that matter most.
Root cause
State is conveyed purely through class/colour changes.
Fix
Add aria-live="polite" to the chip text / banner / toast container, and update an accessible text value on each state change.
Confidence
High
MediumA-03 Green photo headers (.lp-head, .d2-hero, secondary tabs)

White / translucent-white text over a photographic gradient risks failing AA contrast

Issue
Sub-labels use rgba(255,255,255,.82–.88) over assets/bg-green.jpg. Where the photo is light (the lime highlights), white-on-light can drop below the 4.5:1 AA ratio for small text.
Impact
Low-vision users may struggle to read sub-titles, segment labels, and chips on the hero.
Root cause
Text contrast depends on a variable background image rather than a guaranteed dark scrim.
Fix
Strengthen the existing top-gradient scrim under text zones, or use solid white (not translucent) for small labels and verify ≥4.5:1 against the lightest pixels.
Confidence
Low — depends on the image; verify with a contrast tool.
LowA-04 AskEva App - Merged.html · .status-bar icons

Decorative status-bar (signal/battery/clock) is exposed to screen readers

Issue
The fake system status bar (clock "12:24", signal bars, "23" battery) carries no aria-hidden, so it's read aloud as content.
Impact
Screen-reader users hear meaningless chrome ("12 24, 23") before real content on every screen.
Root cause
Device-mock chrome treated as content.
Fix
Add aria-hidden="true" to .status-bar (the real sync chip can live outside it or keep its own label).
Confidence
High
LowA-05 app-shell.merged.js · OTP / 2FA inputs

Six split single-digit inputs lack grouping labels

Issue
The OTP/2FA rows are six separate <input maxlength=1> with auto-advance but no aria-label per box and no group role="group" aria-labelledby.
Impact
Screen readers announce six unlabeled edit fields; users can't tell position ("digit 3 of 6").
Root cause
Visual-only segmented code entry.
Fix
Wrap in role="group" with a label, give each input aria-label="Digit N", and consider inputmode="numeric" autocomplete="one-time-code" on the first.
Confidence
High
05

Performance

MediumP-01 AskEva App - Merged.html · autofill MutationObserver

App-wide observer runs on every DOM insertion across the whole document

Issue
The anti-autofill IIFE does obs.observe(document.documentElement, { childList:true, subtree:true }) and, for every added subtree, calls querySelectorAll("input, textarea") + form sweeps. Modules rebuild large lists via innerHTML (ticketing, leads, dashboards) constantly.
Impact
Every list re-render triggers a full-subtree query and attribute stamping — measurable main-thread churn on big lists and rapid navigation.
Root cause
Broadest-possible observer scope to catch dynamically-rendered inputs.
Fix
Scope the observer to form-bearing containers, throttle/batch via requestIdleCallback, or stamp inputs at render time in each module instead of globally.
Confidence
Medium — mechanism verified; cost scales with render frequency.
LowP-02 notifications.js:263 · profile.js:262

Always-on 1–1.5s polling timers run regardless of route

Issue
setInterval(syncBadges, 1500) (notifications) and setInterval(tickTimers, 1000) (profile) run for the page's whole lifetime, even when their UI isn't visible. They join sync's 52s + 15s heartbeats and leads' 15s reminder poll.
Impact
Continuous wakeups → wasted battery/CPU on a long-lived SPA; syncBadges is a DOM poll that could be event-driven.
Root cause
Polling chosen over event-driven updates.
Fix
Pause timers on visibilitychange (hidden) and when the owning route isn't active; convert syncBadges to fire on the existing leads:changed / notification events.
Confidence
High (existence) / Medium (impact).
LowP-03 <head> · 30 CSS + 45 JS requests

~75 separate, manually cache-busted subresources

Issue
The shell loads ~30 stylesheets and ~45 scripts, each with a hand-maintained ?v=NN. No bundling/minification; render-blocking CSS in the head.
Impact
Many round-trips on first load; easy to ship a stale module by forgetting one version bump (the inline "CACHE-PROOF" notes show this has bitten before).
Root cause
Module-per-feature authoring without a build step.
Fix
Add a bundle/minify step for production (the offline/standalone variants already inline everything — use that path for releases).
Confidence
High
CosmeticP-04 Multiple modules · innerHTML list rebuilds

Full-list innerHTML re-renders on every filter keystroke

Issue
List views (ticketing, contacts, leads) rebuild the entire list via host.innerHTML = list.map(...).join("") on each search/filter change rather than diffing.
Impact
Layout thrash and lost input focus/scroll on large lists; fine at demo data sizes, costly at scale.
Root cause
Stringly-typed rendering without a virtual DOM.
Fix
Debounce search input and, for large lists, update only changed rows.
Confidence
High

Security

prototype · no backend
CriticalS-01 app-shell.merged.js · pwForm / otpForm / maybe2FA

Authentication accepts any well-formed credentials (client-only)

Issue
Password sign-in passes for any RFC-ish email + any ≥4-char password (okEmail/okPw are format checks only). Combined with F-01 (OTP not verified) and F-02 (2FA fail-open), there is no real authentication anywhere.
Impact
Anyone reaching the page is "logged in" as Eshan with full CRM data. All lead/customer/ticket data lives unprotected in localStorage.
Root cause
By design for a no-backend prototype — but it fully satisfies your "weak authentication logic" check and must not ship as-is.
Fix
For production, move auth to a server with real credential verification, signed sessions, and server-side 2FA. For the demo, at minimum gate on a known credential so the flow is honest.
Confidence
High
HighS-02 Many modules · innerHTML with field data

Stored-XSS surface: audit every innerHTML that interpolates user text

Issue
Rendering is string-concatenated innerHTML throughout. Most paths correctly wrap user values in esc()/escapeHtml(), but the pattern is easy to get wrong: a single unescaped lead name, tag, note, company, or ticket subject becomes stored XSS, persisted via localStorage and re-injected on every load. Note also that esc() in sync-layer.js/ticketing.js escapes & < > " but not ' — safe only while values never land in single-quoted attributes.
Impact
If any field reaches innerHTML unescaped, a malicious value typed once executes on every subsequent load for that user.
Root cause
No central templating/escaping guarantee; escaping is per-call discipline.
Fix
Standardize one escaping helper that also handles ', route all dynamic text through it (or use textContent/createElement for user data), and add a lint rule flagging raw interpolation into innerHTML.
Confidence
Medium — escaping is widespread; a full path-by-path verification of every field was not exhaustively completed.
MediumS-03 leads-module.js · localStorage stores

Sensitive CRM data persisted unencrypted in localStorage

Issue
Leads, customers, activity, and preferences are stored in plain localStorage (askeva.leads.v1, askeva.customers.v1, etc.) including names, phone numbers, emails, and notes.
Impact
Any script on the origin, a shared/kiosk device, or browser extension can read all customer PII; it also survives logout (no clear on doLogout()).
Root cause
Client-only persistence model.
Fix
Clear sensitive stores on logout; for production, keep PII server-side and store only a session token.
Confidence
High
MediumS-04 app-shell.merged.js · sign-up vs update-password policy

Inconsistent password policy across flows

Issue
Change-password (updatePwBtn) enforces ≥8 chars + letters&numbers + mismatch/identity checks, while sign-up (suPw) and login accept any ≥4-char string. The strength meter also implies a standard the other flows don't enforce.
Impact
Users can register weak 4-char passwords that the in-app change screen would reject — confusing and weaker than advertised.
Root cause
Validation rules authored independently per screen.
Fix
Extract one validatePassword() and apply it to sign-up, reset, and change consistently.
Confidence
High

Logout doesn't clear session/data — next visitor sees prior user's CRM

Issue

09

Edge Cases

MediumE-01 List rows: .lp-name, .d2-pname, ticket subjects

Long / no-space strings & emoji can overflow or mis-truncate cards

Issue
Names rely on white-space:nowrap; text-overflow:ellipsis in fixed-width rows. A pasted long unbroken string (URL, 100-char "name") truncates, but multi-line fields (descriptions, notes) without overflow-wrap:anywhere can push card width. Emoji in initials avatars (L.name[0]) render a partial surrogate.
Impact
Layout overflow on pathological input; broken avatar glyph for emoji-first names.
Root cause
Ellipsis covers single-line only; initial-letter logic assumes ASCII.
Fix
Add overflow-wrap:anywhere to free-text blocks; compute initials with Array.from(str)[0] to respect surrogate pairs.
Confidence
Medium
MediumE-02 sync-layer.js · flush() / retryItem()

Rapid demo clicks can interleave concurrent flush passes

Issue
flush() is a self-stepping timeout chain over a captured items snapshot. Triggering "Queue a change" / "Make sync fail" repeatedly (or PTR mid-flush) starts overlapping chains that both mutate S.queue and S.syncing.
Impact
Double-counted progress, a row stuck "Syncing", or the chip settling to the wrong state under fast repeated clicks.
Root cause
No re-entrancy guard / in-flight flag on flush().
Fix
Guard with a flushing flag (return early if already running) or coalesce into a single queue processor.
Confidence
Medium
LowE-03 app-shell.merged.js · OTP paste handler

Pasting fewer than 6 digits leaves focus mid-row; non-numeric paste silently dropped

Root cause

Fix
If sanitized paste is empty, show a brief hint; otherwise behavior is acceptable.
Confidence
