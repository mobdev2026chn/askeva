Read this before the score: what AskEva actually is today

The artifact under review is a high-fidelity front-end prototype — a single-device mobile shell running on mock data and localStorage. There is no backend, no real authentication, no live WhatsApp Cloud API connection, and no database. Every "save", "send", "assign" and "payment" is simulated in the browser.

That matters because the audit brief lists ~25 navigation modules, but the real app drawer ships 7: Dashboard, Compose, Chats, Leads, Appointments, Ticketing, Settings (plus Profile/Billing tabs). Contacts, Manage Template, Reports, Flow Builder, Chatbot Builder, AI Agent, WhatsApp Flows, Catalog, standalone Payments & Integrations do not exist as modules — they are roadmap, not product. Scoring "SLA escalation" or "RAG memory" as broken would be dishonest; they were never built. This report separates built-but-flawed from promised-but-absent, because an investor needs to know which is which.

02

Critical Issues — Must Fix Before Any Release

These are release blockers. None can be design-patched; each requires real engineering. Shipping without them is not a soft launch — it is a liability.

Blocker

No backend exists — the app is a browser-only mock

C-01

State lives in localStorage and in-memory JS arrays. There is no server, no persistence across devices, no multi-user concurrency, no source of truth. Two agents cannot see the same inbox; a phone wipe deletes the "CRM".

Stand up an API + database (conversations, contacts, tickets, events) before any other feature work. Everything else in this report assumes this lands first.

Blocker

No real WhatsApp Cloud API / BSP integration

C-02

The product's entire premise is WhatsApp messaging, yet there is no Meta Cloud API connection, no phone-number registration flow, no webhook receiver, no template submission to Meta, and no 24-hour customer-service-window enforcement. Messages are faked bubbles.

Integrate Meta WhatsApp Cloud API (or an embedded-signup BSP path): number onboarding, webhook ingestion, template sync, session-window + messaging-tier limits. Without this there is no product.

Blocker

Authentication is cosmetic; no real identity or session security

C-03

The login screen ships a hard-coded email and password (eshan@tunepath.com / visible password in markup) and "Remember me" is decorative. There is no token issuance, no session expiry, no password hashing, no OTP delivery, no SSO.

Implement real auth: hashed credentials, JWT/refresh rotation, server-validated OTP, forced logout, and SSO/2FA for business accounts. Remove all demo credentials from source.

Blocker

Roles & permissions are unenforced UI

C-04

Settings exposes a Roles screen, but every account sees every module and every record. There is no server-side RBAC, no tenant isolation, no row-level scoping. An "agent" can reach billing, security, and every other contact.

Enforce RBAC on the server for all 7 personas (Agent, Sales, Support, Marketing, Owner, Admin, Super Admin). The client may hide; the API must forbid.

Blocker

No multi-tenant data isolation for a 100k-user SaaS

C-05

There is no concept of an organization/workspace boundary in the data model. For a SaaS onboarding thousands of businesses, cross-tenant leakage is the single most expensive failure mode and there is currently nothing preventing it.

Design tenancy from the schema up (org_id on every row, enforced in every query). Add audit logging of cross-record access.

Blocker

Payments & billing are simulated — no PCI-safe processor wiring

C-06

Razorpay/Stripe/UPI appear as labels and the subscription/transactions tabs render mock rows. No webhooks confirm payment, no invoices are generated server-side, no dunning, no usage metering against WhatsApp conversation costs.

Wire a real processor with server-confirmed webhooks, generated invoices, and usage metering tied to Meta conversation pricing before charging anyone.

06

Chat Module — The Core. Live Chat + History Rework

Chat is the most complete module and the right thing to perfect first. Messaging primitives (text, image, video, doc, voice note, location, contact share, emoji, camera) are present in the UI. The structural problem is lifecycle: there is no Live/History split, and two destructive actions ship that have no place in a CRM.

Built & working (UI level)

Text · Images · Video · Documents · Voice notes · Location · Contact sharing · Emoji/stickers · Camera · Search-in-chat · Mute · Block · Assign/transfer (partial) · Internal notes (partial).

Required

Implement Live Chat + History (24-hour lifecycle)

CH-01

Today every conversation sits in one undifferentiated list. Build a two-tier model:

  • Live Chat — active conversations stay here for 24 hours from the last inbound message (mirrors WhatsApp's customer-service window).
  • History — after 24h a conversation auto-moves to History. Nothing is ever deleted.
  • Search & filters work across both tiers from a single bar, with a Live / History / All toggle.
  • History can be reopened — a new inbound (or agent re-engage within policy) promotes it back to Live.

Model conversation state (live|history) + window_expires_at; a server job demotes on expiry; reopening is an event, not a copy. Index both tiers in one search.

Remove

Delete "Disappearing Messages" and "Clear Chat"

CH-02

Both currently ship in the chat 3-dot menu (data-menu="disappearing", data-menu="clear"). In a CRM these are actively harmful: they destroy the customer record of truth and create compliance gaps. They are consumer-WhatsApp habits that have no place in a business system.

Remove both menu items entirely.

Replace with

Add Export Chat · Download Media · Move to History

CH-03
  • Export Chat — full transcript (PDF/CSV) with timestamps, agent, and notes for audit/handoff.
  • Download Media — bulk-pull every image/doc/voice note from a conversation.
  • Move to History — manual demote for resolved threads (the constructive inverse of "Clear Chat").

These reinforce the "nothing is deleted, everything is retrievable" principle the Live/History model depends on.

Still missing from a real WhatsApp inbox

  • Assignment & routing engine — round-robin, skill/queue-based, load-aware auto-assign (currently manual only).
  • Transfer & merge with context — transfer should carry notes/labels; merge duplicate contacts' threads.
  • Labels, canned replies, and @mentions in internal notes for real team collaboration.
  • Quick-reply / template insertion inside the composer (gated by the 24h window state).
  • Delivery/read receipts driven by real webhooks, not faked ticks.
  • Typing/agent-collision indicator so two agents don't reply to the same customer.

Recommended Navigation Structure

The aspirational nav is a flat list of ~25 items — unusable on mobile and a cognitive overload. Collapse to 5 bottom-tab destinations with grouped sub-sections. Sales sees a pipeline; support sees a queue; everyone shares one inbox.

✗ Today — flat & overloaded

  • Dashboard · Compose · Chat · Contacts · Manage Template · Reports · Flow · Chatbot Builder · AI Agent · WhatsApp Flows · Catalog · Payments · Integration · Leads · Customers · Appointments · Ticketing (Dashboard / Tickets / Settings) · Billing · Settings
  • ~25 peers, no hierarchy, duplicated dashboards, Chat buried mid-list.

✓ Proposed — 5 tabs + grouped drawer

  1. Bottom tabs (always visible)
  2. Home — role-aware dashboard
  3. Inbox — Live Chat · History · Broadcast/Compose
  4. CRM — Leads · Contacts · Customers · Appointments
  5. Desk — Tickets · SLA · Ticket Settings
  6. More — drawer ↓
  7. "More" drawer (grouped)
  8. Automation: Flows · Chatbot · AI Agent · WhatsApp Flows
  9. Growth: Templates · Catalog · Payments · Reports
  10. Admin: Integrations · Billing · Team & Roles · Settings

Principle: the four things an operator does every hour (see, reply, manage, resolve) are one tap away; configuration and building live behind "More". Fix naming too — one "Dashboard", "Chat"→"Inbox", "Compose"→"Broadcast".

10

Security & Performance — For When the Backend Exists

There is nothing to pen-test yet, so this is a build checklist, not a findings list. All items are currently absent.

Security must-haves

  • Hashed passwords (argon2/bcrypt), server-issued JWT + refresh rotation, short session TTL.
  • Server-enforced RBAC + multi-tenant org_id scoping on every query.
  • Real OTP/2FA delivery; SSO (Google/Microsoft) for business plans.
  • Immutable audit log of access & changes.
  • Encryption at rest + in transit; signed, virus-scanned, size-limited file uploads to object storage (not base64 in DB).
  • Webhook signature verification (Meta + payments); secrets in a vault, never in source.
  • Rate limiting, GDPR/DPDP data-export & erasure, PII redaction in logs.

Performance / scale must-haves

  • Cursor pagination + virtualized lists (inbox/contacts will hit 100k+ rows).
  • Server-side search index (conversations + history) — not client filter.
  • Caching layer (Redis) for dashboards & counts; precomputed aggregates.
  • Lazy-loaded media, thumbnails via CDN, signed URLs.
  • Offline queue + optimistic sync + conflict resolution for mobile.
  • WebSocket/push for real-time inbox; FCM/APNs for notifications.
  • Background workers for broadcasts, throttled to Meta tier limits.

12

Features That Can Become AskEva USPs

Competitors are desktop-first, dense, and ugly on a phone. AskEva's polish is real — turn it into defensible differentiation rather than a demo.

  • Genuinely mobile-first WhatsApp CRM — own "run your entire WhatsApp business from your phone". Wati/Interakt are painful on mobile; this is a wedge none defend.
  • AI Agent that takes real actions — not just FAQ deflection, but books appointments, creates tickets, qualifies leads, and writes back to the CRM with memory + RAG over the business's own catalog/docs. This is the single highest-leverage build.
  • "Nothing is ever lost" Live + History model — market the 24h Live → permanent History lifecycle as a compliance & trust feature; pair with one-tap Export/Download for audits.
  • Unified Inbox + Pipeline + Desk in one app — most rivals do one of chat / CRM / helpdesk well. A clean three-in-one for SMBs is a real positioning.
  • Vertical templates — pre-built flows/catalogs for restaurants, clinics, salons, real-estate (the existing demo data already hints at F&B). Fast time-to-value beats generic tools.
  • Owner-grade analytics on a phone — a CEO home screen showing revenue, conversion, and team performance at a glance is something the incumbents bury in desktop reports.

AskEva — Final Production Audit. Brutally honest by request: this is a strong prototype and an unbuilt product. The fastest path to fundable is C-01→C-06, then Chat (Live/History), Templates, Broadcast, and the AI Agent USP — in that order.
