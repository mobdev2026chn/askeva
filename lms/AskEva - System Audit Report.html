Executive summary

AskEva is a client-side mobile CRM: an HTML shell that loads 28 self-contained JavaScript modules, each owning one screen and persisting its own state to the browser's localStorage. There is no server, database, or network API in the codebase — so “database”, “API” and “sync” in the brief all resolve to localStorage reads/writes and in-memory state.

The app is substantially more complete and connected than a typical prototype. Create flows are real (including a working camera business-card scanner), most settings persist, the dashboard computes from live lead data, navigation already preserves scroll position and offers a “back to” return pill, and subscription is a clean single source of truth feeding both Profile and Dashboard. The audit therefore focused on finding the genuine gaps rather than rebuilding working features.

03

Findings & fixes

High✓ Fixed

F1 — Leads were never persisted

Leads are the hub entity — chat sync, the card scanner, the dashboard, companies and lead detail all read the same in-memory array (window.AskEvaLeads). But leads-module.js contained no localStorage calls at all. Every new lead (manual add, card scan, chat sync) and every edit (status, stage, notes, follow-ups, tags) was lost on refresh, while every other major entity persisted.

Added a persisted store askeva.leads.v1: load-into-the-same-array on boot, save after every render and after note/follow-up writes, plus a save on pagehide/tab-hide. Leads now survive refresh and remain the single source of truth.

High✓ Fixed

F2 — Bulk delete orphaned the source of truth

The multi-select Delete action ran LEADS = LEADS.filter(…), reassigning the array. window.AskEvaLeads (and the dashboard's reference) kept pointing at the old array, so deleted leads would silently reappear in other modules — a textbook duplicate-source-of-truth bug.

Switched to an in-place mutation (LEADS.length = 0; push(kept)) so the one shared array reference stays authoritative everywhere, then persist.

Low✓ Fixed

F3 — Duplicate / misleading lead toolbar actions

Export / Sample / Import on the leads toolbar were wired twice: leads-interactions.js does the real work (CSV download, file import), while leads-module.js also fired placeholder toasts (“Exporting all leads…”) that did nothing. Two handlers, one fake.

Removed the placeholder toasts from leads-module.js; the real CSV handlers now own those buttons cleanly.

MediumOpen

F4 — “Team” duplicates “Agents” and doesn't persist

There are two people-management surfaces. Settings → Agents (settings-agents.js) is real, persisted CRUD on askeva.set.agents.v1. Settings → Team (#memList in the shell) is a separate hardcoded list whose Invite, Add department and active toggles update the DOM only — nothing persists, and it's disconnected from the Agents store.

Recommendation: make Agents the single source for people and have Team render from the same store (or retire Team). Deferred because consolidating two UIs safely warrants a focused pass with interactive testing.

MediumOpen

F5 — Lead dashboard reads a one-time snapshot

dash-perf.js snapshots leads with (window.AskEvaLeads || []).slice() at load. After the persistence fix this is correct across refreshes, but in-session edits (new lead, status change) won't reflect in the dashboard until the next reload.

Recommendation: expose a lightweight leads:changed event from leads-module.js and have the dashboard recompute on it. Low risk, additive.

InfoHousekeeping

F6 — Dead handler & duplicate files

  • The shell's .fab-add toast handler matches no elements in the live HTML (appointments/ticketing use their own .appt-fab/.tk-fab with real handlers). Harmless, but it can be removed.
  • ~30 non-loaded duplicate files sit in the project root and uploads/ (AskEva App.html, app-shell.js, lead-profile.js, leads-tools.js, uploads/LMS (Copy)/…). None are referenced by the merged app; archive to reduce confusion.
04

Cross-module synchronization

Already wired — these links exist and work:

Chat → Leads   new WhatsApp chat queues via window.__pendingChatLeads → Leads sync picks it up, de-duped by mobile
Leads → Chat   lead card → window.__openChatFrom() opens the thread and shows a “Back to Lead” return pill
Subscription → Profile + Dashboard   one store (window.__sub) renders plan into both; Upgrade routes Dashboard → Profile → pricing
Leads → Dashboard   dash-perf computes KPIs, pipeline & trends from the live lead dataset

Missing — recommended for a future pass (each is additive; none blocks today's flows):

Appointment ↔ Lead   booking an appointment for a lead should drop an entry on that lead's activity timeline
Ticket ↔ Lead   raising a ticket for a customer should log on the lead's activity (the detail view already mocks ticket rows)
Chat → Appointment / Ticket timeline   creating either from a chat should annotate the chat thread

These require a shared activity model on the lead. Best done as one deliberate pass with a small event bus, after F4/F5 land.

05

Navigation state

  • Scroll position is already remembered per route (scrollMem in the shell) and restored on return.
  • Return context works: opening Chat from Leads shows a “Back to Lead” pill that returns to the exact origin.
  • Filters & selected record persist within a session because each module keeps its own state object and re-renders from it.
  • Panels close cleanly on navigation (subscription wraps the router to dismiss open sheets) — no stale overlays.

Verdict: navigation-state preservation is in good shape. The one enhancement worth making is persisting the active filter set across refresh (today it resets to defaults), which pairs naturally with the F5 live-sync work.
