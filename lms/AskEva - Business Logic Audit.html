1 · Critical logic errors

These are build-blockers. Each one breaks a core CRM guarantee — a stable customer record, no lost demand, an unambiguous owner. Fix the data model for these before anything is implemented.

Critical

There is no Customer entity — "Convert" only relabels the Lead

C-01

Converting a lead simply flips its status to converted and re-titles the badge "Customer." The same row keeps lead-only fields (source, lead score, funnel stage) and there is no separate Customer object with its own lifecycle.

convertLead(L) → L.status = "converted" // no Customer record is created

Consequence: a paying customer who comes back with a new enquiry has nowhere clean to live; the historical lead source permanently mislabels them; and "Customers" as a module can only ever be a filtered view of Leads, not a first-class record with its own tickets, appointments, and payments.

Split Contact (person/number) from Lead (an opportunity) and Customer (a converted relationship). One Contact can carry many Leads over time and one Customer record. Convert should create a Customer, not mutate the Lead.

Critical

Unknown inbound messages create no record — demand can be silently dropped

C-02

When an unknown number messages, the conversation appears in Chat but no Lead, owner, or SLA clock is created. New contacts only become Leads when a human remembers to run Leads → Sync.

"New contacts can be pulled into Leads from the Leads page using Sync." — New-chat modal

A first-touch enquiry can sit unowned and uncounted indefinitely. There is no rule that guarantees every inbound conversation results in a tracked Lead.

Auto-create a Lead (status new, source chat) on first inbound from an unknown number, and assign immediately. Sync becomes a reconciliation backstop, not the primary capture path.

Critical

Capture has no ownership rule — items can exist "Unassigned" with no SLA

C-03

Leads can be created with assigned: "Unassigned", and there is no auto-assignment (round-robin, by-source, or by-availability) at the moment of capture. Chats route to no one automatically.

An unowned record has no accountable agent and no first-response clock — the single most common way real CRM teams leak revenue.

Make ownership mandatory at capture. Define an assignment policy (round-robin within team, or rule-based by source/keyword) and a fallback queue with an SLA timer that escalates if untouched.

Critical

Cross-module links rely on fuzzy contact-matching, not foreign keys

C-04

Appointments, Tickets, and Chat write into a shared activity log by matching on contact (name/number), not by a stable record ID.

AskEvaActivity.log(match, ev) → findLeadByContact(match) // matches by phone/name

If a number is edited, a name differs slightly, or a contact has two leads, the timeline orphans or attaches to the wrong record. Merges and number-changes silently break history — a data-integrity time bomb.

Give every entity a stable ID and link by contactId / customerId. Resolve phone→ID once on ingest; never re-match downstream.

Critical

"Converted" is a terminal dead-end — no churn, re-open, or win-back state

C-05

The status funnel runs new → hot → warm → cold → converted with invalid on the side. After converted there is no defined transition for a customer who churns, lapses, or returns with a new opportunity.

STATUS_ORDER = ["new","hot","warm","cold","converted"] // nothing after converted

Real relationships are cyclical. With no "lost," "churned," or "re-engaged" states, a returning customer re-enters as a brand-new Lead — directly causing the duplication loop in §07.

Separate opportunity states (open/won/lost) from customer states (active/at-risk/churned/reactivated). A won opportunity creates/links a Customer; a new opportunity can open against an existing Customer.

3 · Missing automations

The shared activity log proves the plumbing for automation exists — but the automations themselves are mostly manual today. These are the highest-leverage adds.

Capture & routing

  • Auto-create Lead on first unknown inbound — today: manual Sync
  • Auto-assign on capture (round-robin / rule) — today: none
  • Broadcast reply → route to Lead/Ticket — today: replies unrouted
  • Duplicate detect & merge prompt — today: none

Lifecycle & reminders

  • Auto reminder on appointment booking — today: reminders are manual
  • No-show / cancel → follow-up task — today: dead-ends
  • Post-conversion welcome & onboarding — today: none
  • 24h-window expiry → prompt template — today: window tracked, no action

AI-driven

  • AI Agent → Lead/Ticket/Appointment creation with confidence + human-approval gate — today: undefined

Each automation above must emit a typed event (e.g. lead.created, appointment.booked) so Flow Builder, Reports, and the AI Agent can subscribe — rather than re-deriving state by scanning chats.

Circular

The duplication loop: Customer → new Chat → Sync → new Lead → … forever

F-LOOP

Because converted customers are just leads and returning contacts re-enter through Chat → Sync, an existing customer who messages again spawns a second Lead for the same person — which can itself be "converted" again. Without a unique contact key, the graph loops and fragments one human across many rows.

Break the loop with C-01 + C-04: resolve every inbound to an existing contactId first; open a new opportunity against the existing Customer instead of a new Lead.

5 · Recommended workflow improvements

Sequenced so each step unblocks the next. Treat the first three as pre-development gates.

  • 1 · Model three entities, not one. Contact (the person) ⟶ many Lead/Opportunity records ⟶ one Customer on first win. Everything links by contactId. Resolves C-01, C-04, C-05 and the duplication loop.
  • 2 · Make capture automatic and owned. First inbound from an unknown number creates an assigned Lead with an SLA clock. Resolves C-02, C-03.
  • 3 · Define one event model. Typed events (lead.created, appointment.booked, ticket.resolved, payment.captured) that Flow Builder, AI Agent, Reports, and Dashboard subscribe to — no re-deriving state from chat text.
  • 4 · Write the triage rulebook. Decision table: message intent → Lead / Ticket / Appointment, with the AI's autonomy boundary marked per action.
  • 5 · Close the dead-ends. No-show → follow-up task; cancellation → re-book prompt; resolved ticket → optional follow-up; converted → onboarding sequence.
  • 6 · Add lifecycle states for the post-sale world. Customer: active / at-risk / churned / reactivated — so returning customers re-engage instead of duplicating.
  • 7 · Enforce one identity per human. Unique key on normalized phone; dedupe-on-ingest with a merge prompt.
