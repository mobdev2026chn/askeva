Sync & Real-Time UX Audit · Prototype Review

Does AskEva feel in sync?
A UX-only review of every sync cue the app shows — and the ones it hides.

Reviewed strictly as an interactive mobile UI prototype. This is about what the user sees and trusts — status, freshness, offline, and refresh — not servers, sockets, or databases. Where a state is missing, the fix is a screen, not a backend.

Lens · UX · Interaction · Visual feedback Modules · Chat · Leads · Customers · Appointments · Ticketing Surfaces · Mobile · Tablet · Web Date · 12 Jun 2026

How to read this audit

Per the brief, this looks at AskEva only as an interactive prototype. Backend, APIs, auth, databases, and real network sync are explicitly out of scope — so “sync” here means the visible language of freshness and status: do users know what's saved, what's still going, what failed, what's stale, and how to force a refresh?

Credit where due: AskEva already simulates sync in two places nicely — WhatsApp-style message ticks in Chat and a polished “Sync leads” flow. The gap is that this vocabulary exists in two screens and nowhere else, and that offline, conflict, and multi-device states have no UI at all. This report inventories what's there, then specifies the missing indicators as drop-in design components.

02

What's Already There — and Working

Before the gaps, the wins. These are the sync cues a user can actually see today, and they set the bar the rest of the app should match.

Keep

WhatsApp-style message ticks animate sent → delivered → read

S-01

Outgoing chat bubbles run a three-step tick animation — a single grey check (sent), then a double grey check (delivered), then a double blue check (read) — over roughly a second and a half. It's the single most fluent piece of real-time feedback in the product and reads instantly to anyone who has used WhatsApp.

Gap inside the win: the sequence starts at “sent” — there is no Sending… (in-flight) state and no Failed state, so a message can never visibly “not go through.” See §06 and §07.

Keep

Leads has a real, polished “Sync leads” flow

S-02

The Leads sync sheet shows a spinner, a “Syncing from your channels…” title, per-source rows (WhatsApp · Chat-Sync · Website) that tick off one by one, and a clear success end-state — either “Sync complete · N new leads added” or “You're all caught up”. This is exactly the right pattern: progress, then resolution, then a next action.

This sheet is the template for the whole app's sync language. Lift its spinner, success check, and empty-state copy into a shared component (§07).

Note

Presence & freshness fragments exist — but only in Chat

S-03
  • Presence: conversations show online, typing…, and last seen… states in the chat header — live-status language users understand.
  • Freshness: the catalog card surfaces “synced 2h ago” — the only last-synced timestamp anywhere in the app.
  • Manual refresh: Leads (companies) and Ticketing settings have refresh buttons that re-render with a “Refreshed” toast.
  • Persistence: edits survive a reload via local persistence, so the app feels consistent within one device — the foundation a sync layer would sit on.

The problem is reach: these are one-offs. Presence lives only in Chat, the freshness label only on one catalog card, refresh only in two places. None of it is systematised.

04

Offline Experience

A field-sales or support user on patchy mobile data is the core persona for a WhatsApp CRM. Today the prototype behaves as if the network is always perfect — there is no offline state in the UI at all.

Missing

No offline indicator

OFF-01

Nothing in the shell reacts to connectivity. A user who walks into a lift keeps tapping a UI that looks fully live; actions appear to succeed because everything is local. There is no banner, no dimmed header, no “You're offline” copy.

Add a persistent, low-drama offline banner under the app bar (mock in §07) the moment connectivity drops, and a matching “Back online — syncing” confirmation when it returns.

Missing

No pending-sync indicator or sync queue

OFF-02

When a message or edit can't go through, the user has no idea it's waiting. There is no “1 message pending” chip, no queue screen listing what hasn't synced, and no count anywhere. Work done offline is invisible until — silently — it isn't.

Surface a pending count in the header sync chip, and a tappable Sync queue sheet listing each waiting item with its state (queued / failed). Reuse the Leads sync-sheet layout.

Missing

No retry action for failed work

OFF-03

Because failure is never shown, there's nothing to retry. A real inbox needs a tap-to-retry affordance on a failed message bubble and a Retry all control on the queue.

Add a red failed-message state with a retry icon (§07), plus “Retry” on each queue row and a “Retry all” button on the sheet.

Missing

No conflict-handling screen

OFF-04

If the same lead or ticket is edited in two places, nothing mediates it. There is no “This record changed while you were away — keep yours / keep theirs” prompt. The last write silently wins and the user is never told.

Specify a lightweight conflict sheet: show both versions of the changed fields side by side with Keep mine / Use latest / Merge. Even a simple “refreshed to the newer version” toast is better than silent overwrite.

05

Multi-Device Experience — Mobile · Tablet · Web

Evaluated as a UX question: if the same user (or teammate) opens AskEva on a second screen, does the interface help them trust what they're seeing? Today, nothing in the UI acknowledges that other sessions exist.

✗ Gaps a multi-screen user hits

  • State consistency — no “updated just now” or freshness marker, so a user can't tell whether the screen reflects the latest changes from their other device.
  • Real-time updates — lists never animate in a new item; a returning tab looks frozen with no “1 new” pill to pull.
  • Duplicated actions — no agent-collision cue in Chat, so two people can reply to the same customer with no warning. The Leads sync can also re-add an existing contact as a new row.
  • Stale-data cues — there is no “this view may be out of date” state and no auto/manual refresh prompt after the app has been backgrounded.

✓ What to add (all UI-level)

  • Freshness stamp — a “Synced · just now / 4m ago” line in each module header (§07).
  • “N new” pull pill — a tappable chip at the top of lists when newer data is available, instead of silently redrawing.
  • Collision banner — “Kavya is also viewing this chat” / “…is typing a reply” in shared threads.
  • Stale veil — after long inactivity, a subtle “Refreshing…” overlay on first focus so the user knows the view is catching up.

Responsiveness note: layouts already reflow to tablet/web widths, so the surfaces exist — what's absent is the cross-session trust language that makes using two of them at once feel safe.

08

What to Build First

Sequenced by trust-per-effort. Every item is a front-end component; none waits on a backend to be designed and prototyped.

  • 1 · Ship the status chip system-wide. Put the green / yellow / red chip + “last synced” stamp in every module header. One component, instant consistency, kills most of the “is this current?” ambiguity.
  • 2 · Complete the message states. Add Sending and Failed · tap to retry to the existing tick animation. Smallest change, highest day-one payoff in the core screen.
  • 3 · Add the offline banner + pending queue. Banner on connectivity loss, a count in the chip, and the retry sheet. This is the whole offline story, told in two components.
  • 4 · Pull-to-refresh everywhere. Reuse the green spinner across all four lists; it's the gesture users will reach for first.
  • 5 · Loading skeletons + real success feedback. Replace instant-populate with skeletons, and give status/reschedule/assignment edits a proper “saved & synced” confirmation.
  • 6 · Conflict & collision cues. The agent-collision banner in Chat and a simple “keep mine / use latest” sheet on records — last, because they're the rarest hit but the highest-stakes when missed.

Net: AskEva already speaks fluent “sync” in two screens. The work isn't inventing a language — it's teaching the rest of the app the one Chat and Leads already know.
